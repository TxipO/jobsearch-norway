# Roadmap

Живий документ. Оновлюється по ходу роботи, не переписується з нуля щоразу —
статуси міняються, пункти закриваються, нові додаються знизу відповідної фази.

Профіль користувача, критерії пошуку і рішення по напрямках — у
`profile/profile.md` і пам'яті проєкту (`jobsearch-norway-profile`,
`jobsearch-norway-sources`), не тут. Тут — тільки технічний план.

## Де ми зараз (2026-07-17)

Готово й перевірено на живих даних:
- NAV Arbeidsplassen — sync працює, паралельні детал-запити, ~140 активних вакансій
- SQLite-схема: user_status, source, language, score, score_breakdown, excluded/exclusion_reason
- Rule-based скоринг: IT-support трек, general entry-level трек (retail/customer service/логістика), dev/security трек, remote/локація/мова бонуси, senior/fagbrev/degree/car штрафи
- Hard-block фільтр: медична авторизація, педагогічна освіта, академічні позиції, fagbrev-професії, права/сертифікати, регульовані юр/фін професії — приховані за замовчуванням, видимі за перемикачем
- Веб-інтерфейс (FastAPI + HTMX): список з фільтрами й сортуванням за score, деталі вакансії з розбивкою скорингу, статуси заявок, кнопка "Sync now", посилання на джерело
- Генератор промпта резюме+søknad (MVP без API-ключа — копіюєш промпт вручну)
- Git-репозиторій приватний: `github.com/TxipO/jobsearch-norway`, `/full-review` пройшов чисто
- **Три джерела вакансій:** NAV, Jobbnorge (вся Норвегія), finn.no (Gmail-дайджест). ~2000 активних, 762 відсіяно (hard_blocks + дублікати). Скоринг/фільтр джерело-агностичні без змін.
- **Зарплата** показується в картці/деталях, коли пряма вказана в описі (`kr NNN NNN`, ~28% покриття)
- **CV+søknad білдер переписано** — детермінований `python-docx`, модель повертає лише JSON з фактами, не пише документ сама. Один майстер-CV (`profile/generated/master-cv.docx`), søknad генерується під кожну вакансію окремо. Диплом бакалавра підтверджено як такий, що визнається (HK-dir automatisk godkjenning) — стара версія профілю це заперечувала помилково.
- **Норвезький варіант CV — ГОТОВО (2026-07-17).** `build_cv`/`build_cv_general` приймають `lang="en"|"no"`. Кожен факт (job title/description, EDUCATION, HARD_SKILLS, SOFT_SKILLS, LANGUAGES, обидва summary) має паралельне `_no`-поле в `profile_data.py`. Проперні назви (компанії, ВНЗ, дати) без перекладу. 4 майстер-CV на робочому столі: EN/NO × relevant-split/general.
- **Kanban-вигляд, індикатор "нове", дедлайн-бейдж, лічильник high-score, показ згенерованих документів — ГОТОВО (2026-07-17).** `/kanban` (interesting→archived), бейдж "Нове" на картках з'явлених з останнього sync, бейдж "закривається за N дн." + сортування за дедлайном, лічильник нових high-score вакансій у sync-барі, кнопки завантаження вже згенерованих `cv.docx`/`soknad.docx` на сторінці вакансії.
- **Reachability (громадський транспорт) — ГОТОВО, звужений обсяг (2026-07-17).** `reachability.py`: Entur Geocoder + Journey Planner v3 (безкоштовно, без ключа). Лічиться **лениво** — тільки коли відкриваєш конкретну вакансію, кешується назавжди через `feed_state`. Свідомо НЕ пакетний прорахунок по всіх ~290 унікальних муніципалітетах при кожному sync (невідомі rate-limits, ризик уповільнити sync на хвилини) і НЕ вплетено в score (нема емпіричної ваги, як в інших сигналів скорингу) — суто інформаційний бейдж на сторінці деталей.

## Пріоритет 1 — Другий реальний потік даних

### 1.1 Інтеграція Jobbnorge — ГОТОВО (2026-07-17)
Повний опис вакансій довантажується через недокументований `id.jobbnorge.no/api/joblisting` (74% success rate, решта — фолбек на `summary`, ніколи не валить sync). County-резолюція 93% (складені саамсько-норвезькі назви муніципалітетів + офіційний реєстр поштових індексів Bring/Posten). `extent_percent` парситься консервативно (тільки поруч зі словом "stilling" у тілі опису — голий `N%` ловив нерелевантні цифри типу "95% customer satisfaction"). Деталі — в пам'яті проєкту `jobsearch-norway-sources`.

### 1.2 Webcruiter — ПЕРЕВІРЕНО 2026-07-17, НЕ ПІДХОДИТЬ
Архітектурний тупик, не список ускладнень: кожен роботодавець на своєму піддомені (`8766.webcruiter.no` тощо), єдиної центральної точки з усіма вакансіями всіх роботодавців не існує в принципі. Обидва офіційні API (Webcruiter Public API, Career Site API) вимагають OAuth конкретного орендаря — це інтеграційний інструмент для HR-відділів, не публічний пошук. Не повертатись без нових фактів.

### 1.3 Дедуплікація між джерелами — ГОТОВО (2026-07-17)
Спершу зміряв на живих даних, перш ніж будувати: **лише 3 підтверджені дублікати з ~2000 активних вакансій** (0.15%), усі NAV+finn.no, **0 перетинів NAV+Jobbnorge**. Набагато менша проблема, ніж очікувалось при написанні плану — повний merge/relink UI не виправданий на такому масштабі. Реалізовано легше: `scoring._exclude_cross_source_duplicates()` — ключ (нормалізований employer_name без AS/ASA-суфіксів, title, municipal), серед груп із 2+ джерел лишає найвищий score, решту позначає через уже наявний `excluded`/`exclusion_reason` (та сама механіка, що hard_blocks — оборотно через "показати все одно", нічого не видаляється). 5 тестів у `tests/test_dedup.py`, включно з перевіркою, що REMA 1000 в різних містах не схлопується (municipal — частина ключа).

### 1.4 finn.no парсер — ГОТОВО (2026-07-17)
Перший лист прийшов, структуру розпарсено: `finn_client.py`, блоки розділені лінією тире, title+employer+location — два рядки перед `Flere detaljer:` URL. **Опису нема** — finn.no's robots.txt забороняє fetch сторінки оголошення (на відміну від Jobbnorge), скоринг для цього джерела працює лише по назві. Вплетено в `sync.py` й `/sync`-роут з окремим try/except (Gmail auth-збій не валить NAV/Jobbnorge).

### 1.4a Позичання опису з NAV/Jobbnorge для finn.no — ГОТОВО (2026-07-18)
Обхід finn.no's захисту (Cloudflare, заборона в robots.txt) розглянуто і свідомо відхилено — ризик бану акаунта на головному job-борді Норвегії непропорційний вигоді. Замість цього: перевірено й HTML-варіант листа (перед цим парсився лише plain-text) — видимого тексту там теж лише title/роботодавець/локація, жодного опису, 90% зайвих байтів це CSS. Легальна альтернатива: `scoring._build_description_lender_lookup()` — той самий dedup-ключ (роботодавець+назва+муніципалітет), що вже ловить крос-джерельні дублікати, тепер ще й "позичає" опис із NAV/Jobbnorge рядка для скорингу finn-вакансії. **Виміряно на живих даних: 11 з 60 (18%)** — не 19/60, як здавалось при матчингу лише по роботодавцю (великий роботодавець типу "Bergen kommune" публікує десятки різних вакансій одночасно — без назви в ключі можна позичити опис геть іншої вакансії). Позичений опис явно позначений (`description_borrowed_from` колонка + банер на сторінці деталей з посиланням на джерело). Попутно виправлено баг: `upsert_vacancy_row`'s upsert затирав позичений опис на кожен наступний finn-sync (`description=None` завжди в finn_client) — той самий клас багу, що вже був з Jobbnorge full-description backfill, тепер `COALESCE`.

### 1.5 Teamtailor (пізніше, за потреби)
Той самий тип обмеження, що й Webcruiter — публічний JSON-фід є на кожному career-сайті окремо, але немає єдиної центральної точки. Має сенс тільки якщо з'явиться конкретний список компаній-цілей.

### 1.6 EasyCruit (Sogndal kommune) — ГОТОВО, звужений обсяг (2026-07-19)
**EasyCruit як 4-те нацйональне джерело — ПЕРЕВІРЕНО, той самий глухий кут, що Webcruiter.** Кожен роботодавець на своєму піддомені (`sogndal.easycruit.com`), офіційний "Public API" — тільки OAuth2 per-tenant для звітності роботодавця, не для читання вакансій сторонніми. Не будувати як загальне джерело.

**Але сам Sogndal kommune — окремо, реалізовано `easycruit_client.py`.** Це саме та муніципалітет-пріоритет №1 користувача, і виміряно: 0 з 13 активних вакансій там перетинаються з тим, що вже приходить через NAV/Jobbnorge — реально нове джерело. robots.txt дозволяє все, крім `/intranet/`. Технічна особливість: головна сторінка зі списком захищена AWS WAF JS-челленджем (`x-amzn-waf-action: challenge`, HTTP 202 на голий `requests.get`), а сторінки деталей окремих вакансій — ні (200 OK, повний HTML). Замість додавання Playwright (важкий dependency, ~300MB) заради 13 вакансій одного роботодавця: список ID оновлюється вручну (Claude відкриває список через Browser pane, копіює `/vacancy/{id}/{dept}` посилання), зберігається в `feed_state` через `easycruit_client.set_known_ids()`; `sync()` тягне лише WAF-вільні сторінки деталей звичайним `requests`.

Живий баг, спійманий при першому наповненні даними: сервер не вказує charset у `Content-Type`, `requests` хибно вгадує ISO-8859-1 замість UTF-8 — усі æ/ø/å ставали мойибейком ("på" → "pÃ¥"). Виправлено — `resp.content.decode("utf-8")` напряму, не покладатись на `resp.text`.

## Пріоритет 2 — Скоринг: уточнення (LLM-рівень відкладено)

**Рішення прийнято 2026-07-17: без Anthropic API ключа — грошей на це нема.** LLM-скоринг і автогенерація резюме через API закриті як напрямок. Замість цього: користувач сам копіює промпт (кнопка "Згенерувати CV + søknad") і вставляє в чат Claude Code — той самий результат, без витрат, бо це вже включено в наявну підписку. Не повертатись до питання API-ключа, поки користувач сам не підніме.

- [x] **Емпіричний аудит keyword-списків — ГОТОВО (2026-07-18).** Перевірено кандидатів на розширення (systemadministrator/it-drift/superbruker/tekniker тощо) — жоден не пройшов планку "підтверджено фактом з профілю" з реальних даних, нічого не додано. Натомість знайдено й виправлено реальний **false positive**: bare `"lager"` (мало ловити "склад/warehouse") збігалося з норвезьким дієсловом "å lage" ("робити/створювати" — "produktene vi lager..."), назвою будівлі ("havnelageret") і навіть словом "klager" (скарги) як підрядковий збіг. 61 з ~1300 активних вакансій мали цей хибний збіг; після видалення bare-слова (лишили точніше `lagermedarbeider`) — 0. Перерахунок застосовано одразу на живій БД, не тільки для майбутніх sync.
- [x] **Фільтр за score в UI — вже зроблено раніше цієї сесії** (min_score), пункт застарів.

## Пріоритет 4 — UX і масштабування списку

- [x] **Пагінація — ГОТОВО (2026-07-17).** 50/сторінку, `count_vacancies`/`list_vacancies` діляють один білдер фільтрів. Перевірено: сторінка 2 працює, overshoot (page=999) коректно кліпається до останньої, фільтри зберігаються між сторінками.
- [x] **Автоочистка — ГОТОВО (2026-07-17).** `delete_inactive()` — видаляє те, що джерело саме позначило неактивним (це вимога умов використання NAV, не просто зручність). `delete_expired_unreacted()` — видаляє прострочені вакансії зі статусом "new" (те, на що не відреагував); вакансії зі статусом interesting/applied/interview/rejected/archived НЕ чіпає — це твоя історія заявок. Перевірено синтетичним тестом (expired+new видалилось, expired+applied лишилось). Обидві вплетені в кожен sync.
- [x] **Фільтри по score і зарплаті — ГОТОВО (2026-07-17).** `min_score` (score >= N) і `min_salary` (salary_min >= N) у формі фільтрів, ті самі query-параметри переживають пагінацію. `salary_min` — нова колонка (перше число з salary_text, роздільники тисяч прибрані) — свідомо НЕ видається за нормалізовану річну/місячну ставку (оголошення плутають періоди), лише груба ручка для порівняння. Бекфілиться при кожному rescore.
- [x] **Кнопка "🚩 Помилка" — ГОТОВО (2026-07-19).** Користувач попросив спосіб позначити вакансію, що явно не мала пройти фільтри (старі/зламані записи), без написання пояснення — щоб Клод сам розбирав чергу пізніше й шукав патерни (та сама методика, що вже дала фікси junior/delivery/remote/lager цієї сесії, тільки за user-driven вибіркою, не ручним семплінгом). Нова `flagged_at` колонка (timestamp, не bool — для `db.list_flagged()` найстаріші-перші), окрема вісь від `user_status` і `excluded`. Позначені вакансії ховаються зі списку за замовчуванням (той самий патерн, що й excluded — банер+лічильник+"показати все одно"), так що фіча одразу вирішує і захаращення списку, і чергу для аналізу.
- [x] **Мобільна перевірка CSS — ГОТОВО (2026-07-18).** Перевірено index/kanban/detail на 375px через Browser pane (JS-перевірка `scrollWidth`, не скріншот — панель зависала). Знайдено й виправлено реальний баг: бейджі "Нове"/дедлайну переносились на новий рядок під заголовком замість того, щоб стояти поруч (`.vacancy-title` було `display:block`) — баг на БУДЬ-якій ширині екрана, не тільки мобільній. Виправлено через `.vacancy-title-row` (flex). Немає горизонтального overflow на жодній із трьох сторінок.
- [x] **Позначення "нове з останнього sync" — ГОТОВО (2026-07-17).** `PREV_SYNC_AT_KEY` зберігає timestamp попереднього sync до перезапису; `first_seen_at > new_since` → бейдж "Нове".
- [x] **Kanban-вигляд по user_status — ГОТОВО (2026-07-17).** `/kanban`, колонки interesting→archived (не new — це весь бэклог, лишається в списку).

## Відкриті рішення, які чекають на відповідь користувача
